# Проект: система воздействия на должников для ТНС Энерго

Этот файл — общий контекст проекта для Claude Code и для команды. Он лежит в корне репозитория, Claude читает его автоматически. Обновляйте его, когда меняются договорённости.

## Цель

Был хакатон (2-е место). Через полгода ТНС Энерго захотела внедрить решение. Требования заказчика:

1. **Автоматизировать ручной труд.** Каждый месяц сотрудники вручную решают, какому должнику какую меру применить (СМС, звонок, претензия, выезд, уведомление, ограничение, суд). Это должна делать программа.
2. **Объяснимость.** По каждому лицевому счёту (ЛС) должно быть видно, почему выбрана именно эта мера.
3. **Веб-приложение на сервере заказчика** (изменено 06.11.2026, раньше было «локальный запуск на компьютере»). Бэкенд работает на одном сервере во внутренней сети ТНС Энерго, из интернета недоступен, без облака. Определённые сотрудники открывают интерфейс по ссылке в браузере после входа. Подробности — раздел «Веб-приложение» ниже и `docs/web_app_plan.md`.
4. **ML оставляем.** Заказчик хочет ML-составляющую. Результаты пойдут и во внедрение, и на конференцию, поэтому ML должен быть честным: без утечек и с корректной проверкой.

## Архитектура новой версии

```
файлы 01–14 → загрузка и проверка → панель «ЛС × месяц»
  → исключения → машина стадий → движок правил (кандидаты на меры с кодами причин)
  → ML-скор (вероятность самостоятельной оплаты)
  → аллокатор под месячные лимиты → реестры по мерам + план + объяснения
```

- **Правила решают «кому можно»**: регламент, разложенный на правила с кодами (`docs/Правила воздействия ТНС v0.2.xlsx`).
- **ML решает «кому в первую очередь»**, когда кандидатов больше лимита. Приоритет = ДЗ × (1 − p_оплаты). ML не может назначить меру, которую не разрешили правила.
- **Аллокатор** раздаёт меры с лимитом по очереди приоритета, начиная с самых дефицитных (ограничение 200, выезд 500, СМС 2 150 в месяц).
- **Кластеризация в рабочем пайплайне не участвует.**

### Известные проблемы хакатонной версии (не повторять)

- **Утечка данных:** признаки посчитаны один раз на 2026-02, а события для обучения взяты с 2025-01. Модель «видела будущее», поэтому AUC 0.84–0.97 завышен.
- **Selection bias:** propensity AUC 0.99–1.00. Uplift-оценки («претензия снижает оплату на 27%») — артефакт.
- **Стадия** считается как «самая тяжёлая мера за всё время», без учёта погашения.
- **Названия сегментов** захардкожены и разъехались с содержимым кластеров.
- **Охват:** меры назначены ~15 тыс. ЛС при ~60 тыс. должников с ДЗ ≥ 500 ₽. Уведомления использованы на 16% лимита.
- **E-mail** завязан на `has_ebill` (эл. квитанция), а не на наличие адреса.
- **Объяснения** противоречат назначенным мерам (мера снята по лимиту, а текст остался).
- **Запуск через GUI** упал на шаге 4 из-за отсутствующего `pyyaml`. Нужны зафиксированные зависимости.

## Ответ заказчика (31.10.2026)

- **Результат меры:** оплата не менее 30% задолженности до конца месяца, следующего за расчётным. Это параметр P-03/P-04 в правилах и **таргет ML-модели**.
- **Срок просрочки:** месяцы с даты образования задолженности. Срок оплаты — до 15-го числа месяца, следующего за расчётным; с 16-го долг просрочен.
- **Двукратный норматив:** расчётная величина, заказчик подготовит выгрузку. Пока её нет — прокси 2 × среднее начисление за 12 мес.
- **Текущая практика отбора** (это базовая линия, с которой сравниваем ML):
  1. срок задолженности 1–3 мес. (реже до 6);
  2. нет соглашения о реструктуризации и нет введённого ограничения;
  3. долг > 1 000 ₽, затем порог по сумме поднимают, пока кандидаты не уложатся в лимит (= сортировка по убыванию долга);
  4. СМС — в приоритете максимальный долг.

### Открытые вопросы (созвон, задача ORG-5)

- К каким мерам относятся порог 1 000 ₽ и срок 1–3 мес.?
- 30% — от всего долга или от просроченной части?
- Как разносятся оплаты по периодам: FIFO или по периоду из платёжки? Пока считаем FIFO.
- Формат выгрузки норматива, признак реструктуризации, дата снятия ограничения.
- Согласие на пилот 1–2 мес. с двумя очередями.

## ML-часть (ведёт Алексей)

- **Задача:** скоринг «заплатит ли ЛС сам ≥ 30% долга до конца месяца». Это не uplift и не оценка эффекта мер.
- **Обучающая выборка:** помесячные срезы 2025-07…2026-01. Одна строка = ЛС-должник на 1-е число месяца. Признаки строго на дату среза, таргет — после.
- **Валидация по времени:** обучение 2025-07…10, валидация 2025-11, тест 2025-12…2026-01. Случайное перемешивание запрещено.
- **Модели по ступеням:**
  - 0 — сортировка по сумме долга (текущая практика);
  - 1 — скоринговая карта (биннинг + логрег);
  - 2 — LightGBM/CatBoost с монотонными ограничениями + калибровка.
- **Главная метрика — бэктест очереди:** сколько реально неоплаченного долга попадает в лимит. Плюс AUC (реалистично 0.75–0.85; > 0.95 — подозрение на утечку) и калибровка.
- **Ограничение бэктеста:** история показывает результат старой практики. Прирост сборов доказывает только пилот.
- **Объяснения:** SHAP-топ-3 или баллы карты с человекочитаемыми названиями признаков.

## Веб-приложение (ведёт Женя)

План по шагам — `docs/web_app_plan.md`. Договорённости:

- **Стек:** FastAPI + uvicorn, шаблоны Jinja2, свои CSS/JS без CDN (в сети заказчика может не быть интернета). Хранилище — SQLite (`storage/app.db`): пользователи, наборы данных, запуски, журнал действий.
- **Где код:** `tns/web/` (`app.py`, `auth.py`, `db.py`, `templates/`, `static/`); точка запуска — `web.py` в корне. Настройки — раздел `web:` в `configs/settings.yaml`, секреты (ключ сессий, пароль LDAP) — только в переменных окружения.
- **Одно приложение, разные настройки:** на своём компьютере — `http://127.0.0.1:8000`, свои логины (`auth: local`); на сервере ТНС — HTTPS через nginx, вход через Active Directory (`auth: ldap`). Отдельной «упрощённой» версии не делаем.
- **План строит `run.py` отдельным процессом** (`subprocess`), не импортом пайплайна в веб-сервер: изоляция памяти, возможность остановить запуск, свой журнал (`TNS_LOG_DIR`). Прогресс — строки «Шаг N/9» из вывода, ошибки — тексты из `tns/logs.py`. Одновременно выполняется один запуск, остальные ждут в очереди.
- **Данные на сервере:** `storage/datasets/<id>/` — загруженные файлы 01–14, `storage/runs/<id>/` — результаты и журнал запуска. Папка `storage/` в git не попадает.
- **Роли:** администратор (пользователи, настройки), аналитик (загрузка, проверка, запуск, скачивание), наблюдатель (просмотр и скачивание). Права проверяются на каждом endpoint, а не только скрытием кнопок.
- **Персональные данные должников:** сервер слушает только `127.0.0.1` за nginx, наружу не публикуется; пути из запросов проверяются (никаких `../`); вход, загрузка, запуск и скачивание пишутся в журнал действий; пользователю — сообщения без трассировок и путей сервера.
- **Тесты:** `tests/test_web.py` на `fastapi.testclient.TestClient` и мини-данных из `tests/conftest.py`.

## Правила работы в репозитории

- Python + pandas. Сервер ТНС во внутренней сети может быть без интернета: установка — из готового архива (Docker-образ или заранее скачанные пакеты), страницы не грузят ничего из интернета. Все зависимости — с точными версиями в `requirements.txt`.
- Файлы в `Материалы к кейсу/` не изменять.
- Любой признак для ML считается только по данным до даты среза.
- Пороги и параметры не хардкодить: правила — в таблице правил, остальное — в конфиге.
- Комментарии и сообщения об ошибках — на русском, понятные пользователю.
