# Рекомендательная система: run_recommendations

Скрипт `scripts/build_recommendations.py` — главный исполнительный модуль системы.  
Принимает сегментацию, uplift-матрицу и историю мер; возвращает **персональный план мер на месяц** для каждого ЛС с учётом:
- правил допустимости Приложения №1,
- очередности процедур (Информирование → Ограничение → Суд),
- комбинаций мер (фоновые + ведущая),
- лимитов Приложения №2.

## Быстрый запуск

```bash
pip install pandas numpy pyyaml openpyxl pyarrow

python scripts/build_recommendations.py \
    --data-dir "Материалы к кейсу" \
    --features output/kprototypes_features.parquet \
    --utility  output/utility_matrix.parquet \
    --labels   output/kprototypes_labels.csv \
    --config   configs/ \
    --month    2026-02 \
    --out      output/recommendations_2026-02.csv
```

Время выполнения: ~20-30 секунд на 136K ЛС.

## End-to-end (полный пайплайн)

```bash
# Шаг 1: признаки
python scripts/build_kprototypes_features.py --data-dir "Материалы к кейсу"

# Шаг 2: сегментация
python scripts/run_kprototypes_segmentation.py

# Шаг 3: uplift-модели (~3-5 мин)
python scripts/build_response_models.py --data-dir "Материалы к кейсу"

# Шаг 4: рекомендации
python scripts/build_recommendations.py --month 2026-02
```

Или через GUI: запустить `python interface.py` → нажать **«Сформировать план мер на месяц»**.

| Аргумент | По умолчанию | Описание |
|---|---|---|
| `--data-dir` | `Материалы к кейсу` | Папка с исходными xlsx/csv файлами |
| `--features` | `output/kprototypes_features.parquet` | Признаки ЛС |
| `--utility` | `output/utility_matrix.parquet` | Матрица uplift/ERG |

## Конфигурация

### `configs/rules.yaml` — Приложение №1

Для каждой меры задаёт:
- `min_overdue_months` / `max_overdue_months` — диапазон срока ДЗ
- `min_dz` / `max_dz` — диапазон суммы ДЗ
- `requires_phone` / `requires_email` — наличие контакта
- `requires_prev_stage` — требование предыдущей стадии (например, сначала информирование, потом ограничение)
- `dz_times_norm_min` — ДЗ > N × норматив потребления
- `is_background` — фоновая мера (применяется совместно с другими)

### `configs/limits.yaml` — Приложение №2

Месячные лимиты на каждую меру:

| Мера | Лимит |
|---|---|
| Автодозвон | 8 000 |
| E-mail | без ограничений |
| СМС | 2 150 |
| Обзвон оператором | 1 550 |
| Претензия | 400 |
| Выезд | 500 |
| Уведомление об ограничении | 6 200 |
| Ограничение | 200 |
| Заявление о судебном приказе | 400 |

### `configs/costs.yaml` — cost_tier

Порядковая шкала ресурсоёмкости (1 = минимальные, 5 = максимальные).  
Используется для разрешения ничьих при одинаковом `expected_recovery_gain`.

> **Рублёвые cost не используются** — реальная себестоимость мер не была предоставлена бизнесом.  
> Для подключения реальных тарифов: заполнить блок `cost_rub` в `configs/costs.yaml`.

## Алгоритм (блоки)

### 1. State machine (очерёдность процедур)

По истории мер (файлы 04–13) для каждого ЛС определяется текущая стадия:
- `unknown` → `informing` → `restriction_notice` → `restriction` → `court`

Флаги `can_do_restriction`, `can_do_court` управляют доступностью следующих стадий.

### 2. Eligibility по Приложению №1

Булева матрица `eligible[ЛС, мера]` — допустимо ли назначить меру с учётом:
- срока и суммы ДЗ,
- наличия контактов,
- достигнутой стадии,
- нормативного порога потребления.

### 3. Combo builder

Для каждого ЛС формируется лучший action_set:
- **фон**: E-mail (если `has_ebill`) + Автодозвон (если `has_phone` и eligible)
- **ведущая мера**: лучшая по `expected_recovery_gain` среди eligible ведущих мер; при равенстве — меньший `cost_tier`
- `set_erg = Σ expected_recovery_gain(i, m)`

### 4. Жадный аллокатор (Приложение №2)

**Два прохода**:
1. «Горячие» ЛС (сегменты 0, 1 — высокий DZ) — в приоритете
2. Остальные — по убыванию `set_erg`

**При нехватке лимита**: снимается ведущая мера, назначается только фон.

### 5. Объяснения

Для каждого назначения формируется текстовое объяснение:

> «Сегмент 1 — "Средняя задолженность (уведомление ограничения)". ДЗ: 2 500 руб., просрочка: 3 мес., payment_ratio_12m: 0.45. Ведущая мера: "Уведомление об ограничении" — ожидаемый прирост возврата ≈ 820 руб. (cost_tier=2, затраты низкие). Назначены меры: "E-mail рассылка", "Уведомление об ограничении". Условия Приложения №1 выполнены: ДЗ ≥ 1 500 руб.; просрочка ≥ 1 мес.; информирование применялось.»

## Выходные файлы

### `output/recommendations_YYYY-MM.csv`

| Колонка | Описание |
|---|---|
| `ls` | Лицевой счёт |
| `segment` | Номер сегмента |
| `segment_name` | Название сегмента |
| `DZ_current` | Текущая ДЗ, руб. |
| `overdue_months` | Срок просрочки, мес. (прокси: max_consecutive_nonpayment) |
| `measures` | Назначенные меры через `;` |
| `leading_measure` | Ведущая мера |
| `leading_erg` | ERG ведущей меры, руб. |
| `set_expected_recovery_gain` | Суммарный ERG action_set, руб. |
| `set_cost_tier` | Сумма cost_tier мер набора |
| `top_uplift_measure` | Мера с наибольшим uplift |
| `top_uplift_value` | Значение uplift |
| `assigned` | Назначена ли хотя бы одна мера |
| `explanation` | Текстовое объяснение |

### `output/recommendations_summary.csv`

Агрегаты по мерам: `assigned_count`, `limit`, `utilization`.

## Известные ограничения

1. `overdue_months` в текущих features-parquet заменён прокси `max_consecutive_nonpayment` (до пересчёта признаков).
2. Selection bias в uplift-моделях: для production рекомендуется DR-learner.
3. Рублёвые тарифы себестоимости не подключены; `cost_tier` используется только для tie-breaking.
