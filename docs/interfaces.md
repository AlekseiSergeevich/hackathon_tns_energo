Версия 0.1 от 02.11.2026. Решения принял Алексей, обсуждаем на созвоне ORG-2. Открытые вопросы собраны в конце.

**Обновлено 06.11.2026 (Аня):** раздел 4 «Стадии» — машина стадий реализована (`tns/rules/stages.py`), добавлены колонки `stage_fact`, `stage_source`, `reason` и правила расчёта; таблица правил v0.3 сделана; «Открытые вопросы» — решения по стадиям.

## Схема

```
файлы 01–14 ─► ls_info ─────────────┐
            ─► panel ───────────────┼─► stages ─► candidates ─┐
            ─► measure_events ──────┘                         ├─► аллокатор ─► plan + реестры
                       panel + ls_info + stages ─► score ─────┘
```

| Таблица | Файл | Строит | Модуль | Одна строка |
|---|---|---|---|---|
| Анкета ЛС | `ls_info.parquet` | Женя | `tns/data/panel.py` | ЛС |
| Панель | `panel.parquet` | Женя | `tns/data/panel.py` | ЛС × месяц |
| Журнал мер | `measure_events.parquet` | Женя | `tns/data/panel.py` | ЛС × мера × месяц |
| Стадии | `stages.parquet` | Аня | `tns/rules/stages.py` (готово) | ЛС × месяц |
| Кандидаты | `candidates.parquet` | Аня | `tns/rules/engine.py` | ЛС × месяц × мера |
| Скор | `score.parquet` | Алексей | `tns/ml/` | ЛС × месяц |
| План (выход аллокатора) | `plan.parquet` | Аня | `tns/alloc/` | ЛС × месяц × мера |

Сырые файлы 01–14 читает только `tns/data`. Остальные части работают с таблицами из этого документа.

## Общие соглашения

- `month` — первое число месяца, `datetime64[ns]`.
- `ls` — `int64`, пропусков нет.
- Суммы — `float64`, рубли.
- Флаги — pandas `boolean`; неизвестно = `<NA>`. Строки «Yes/No/Unknown» не используем.
- Категории — `category` с фиксированным списком значений.
- Пусто = `NaN` / `<NA>`.
- Списки кодов (правил, исключений) — строка через `;`, чтобы открывалась в Excel.
- Даты событий — `datetime64[ns]`.
- Хранение — parquet в `output/<YYYY-MM>/`, где `YYYY-MM` — месяц плана.
- Ключи мер — по `MEASURE_FILES`: `autodial, email, sms, operator_call, claim, visit, restriction_notice, restriction, court_application, court_result`. Плюс `commission_list` (R-CRT-04, только в кандидатах и плане).

### Когда известна колонка (`known_at`)

У каждой колонки указано, когда она известна относительно месяца M строки:

- **start** — на 01.M, до каких-либо действий в M (сальдо, стадия, срок просрочки);
- **end** — только после окончания M (начисления, оплаты, меры, результат за M);
- **static** — анкета, один снимок без даты.

**Правило для ML:** признаки среза M берутся только из колонок `start` месяца M и из любых колонок месяцев ≤ M−1. Колонка `end` месяца M — это будущее (таргет живёт там же). Проверяется автотестом ML-3.

### Период данных

2025-01 … **2026-03**. Второй блок «2026-02» в шапке ОСВ (колонки 43–45) — это март 2026:
- «Оплачено» блока совпадает с мартовскими оплатами файла 03 у 99 % ЛС;
- «СЗ на начало» = сальдо + начислено − оплачено первого блока у 96 %.

Настройка `osv.duplicate_month: shift_next` (по умолчанию). При срабатывании в лог пишется предупреждение. Ждём подтверждения заказчика.

## 1. `ls_info` — анкета ЛС

Источник — файл 01. Один снимок на неизвестную дату (вероятно, дата выгрузки), поэтому для старых срезов признаки слегка «из будущего». Учитывать это в ML: смотреть важность этих признаков и не строить на них выводы для конференции.

| Колонка | Тип | Смысл | Откуда | known_at |
|---|---|---|---|---|
| `ls` | int64 | номер ЛС | 01 | — |
| `has_phone` | boolean | есть телефон | 01 «Наличие телефона» | static |
| `has_ebill` | boolean | электронная квитанция | 01 | static |
| `has_benefits` | boolean | есть льготы | 01 | static |
| `not_residing` | boolean | не проживает | 01 | static |
| `remote_disconnect` | boolean | возможно дистанционное отключение | 01 | static |
| `house_type` | category | `ЧД` / `МКД` / `Общежитие` | 01 | static |
| `gasified` | boolean | газифицирован | 01 | static |
| `address_guid` | string | ГУИД адреса | 01 | static |

Отдельных `has_mobile` и `has_email` нет: тип телефона и e-mail в данных отсутствуют, а дублировать колонки бессмысленно. Правила ссылаются на `has_phone` (СМС) и `has_ebill` (e-mail, прокси). Это нужно поправить в таблице правил (см. «Что поменять в таблице правил»).

## 2. `panel` — ЛС × месяц

Финансы ЛС по месяцам. Мер здесь нет, они в `measure_events`.

| Колонка | Тип | Смысл | Откуда / как считаем | known_at |
|---|---|---|---|---|
| `ls` | int64 | номер ЛС | 02 | — |
| `month` | datetime | 1-е число месяца | шапка 02 | — |
| `saldo_start` | float64 | сальдо на 01.M, < 0 = переплата | 02 «СЗ на начало» | start |
| `dz` | float64 | долг на 01.M: `max(0, saldo_start)` | расчёт | start |
| `dz_overdue` | float64 | просроченная часть: `max(0, dz − accrual(M−1))` уточняется по P-02 | 02, FIFO (DATA-5) | start |
| `overdue_m` | Int64 | срок просрочки, мес. (P-02) | 02, FIFO (DATA-5) | start |
| `overdue_censored` | boolean | долг старше 2025-01, срок занижен | 02 | start |
| `months_no_payment` | Int64 | месяцев подряд без оплат перед M | 03 | start |
| `months_no_payment_censored` | boolean | серия тянется с начала данных | 03 | start |
| `norm` | float64 | норматив потребления, ₽, **одинарный** (P-07) | выгрузка заказчика (`norm.customer_file`), где есть значение; иначе прокси: среднее `accrual` за доступные месяцы ≤ M−1 (до 12, минимум 3). Прокси ≤ 0 → пусто | start |
| `norm_source` | category | `customer` / `proxy`; пусто, если норматив не определён | — | start |
| `accrual` | float64 | начислено за M | 02 «Начислено» | end |
| `paid` | float64 | оплачено за M по ОСВ | 02 «Оплачено» | end |
| `paid_payments` | float64 | сумма оплат за M по файлу 03 | 03 | end |
| `pay30_m` | boolean | `paid_payments ≥ 0.30 × dz`; `<NA>`, если `dz = 0` | расчёт; доля — `result.share` в `settings.yaml` | end |

Пояснения:
- **Три колонки долга.** Пороги правил (`dz >= P-01`, «ДЗ от, руб.») и приоритет считаются от `dz`, то есть от всего долга на 01.M. `dz_overdue` — справочно и для возможной смены определения после ответа заказчика.
- **Срок просрочки (P-02, FIFO).** На 01.M счёт за M−1 ещё не просрочен (оплата до 15.M). Срок — месяцы от самого старого непогашенного счёта до M−2 включительно. Оплата, отрицательный перерасчёт и корректировка сальдо вниз гасят самые старые счета; возврат оплаты и корректировка сальдо вверх (сальдо M+1 ≠ сальдо + начислено − оплачено) снова открывают самые свежие оплаченные счета. Долг до 2025-01 — счёт без даты, `overdue_censored = True`. Ручная сверка: `python -m tns.data.overdue_check --month ГГГГ-ММ` → `overdue_check.xlsx`.
- **Норматив** хранится одинарный, кратность — параметр P-08. Условие везде одно: `dz > P-08 * norm`. Выгрузка заказчика подключается в `configs/settings.yaml` (раздел `norm`): путь, названия колонок (ЛС, норматив, необязательный месяц) и кратность числа в файле. Значение с месяцем действует с этого месяца до следующего значения по ЛС, без месяца — для всех месяцев. Пустой `norm` (нет истории или прокси ≤ 0): условие `dz > P-08 * norm` не выполнено.
- **Месяцы без движения (R-VST-05, P-12)** — `months_no_payment`: показаний в данных нет, поэтому «нет движения» = нет оплат. Из-за начала данных (2025-01) условие `months_no_payment > 12` может выполниться не раньше 2026-02.
- **`pay30_m`** — оплата ≥ 30 % от всего `dz` до конца M. Это **таргет ML** и вход для «результата» в правилах. Относится к ЛС за месяц, а не к конкретной мере. Результат конкретной меры — в `measure_events`.
- Оплаты для таргета и результата берутся из файла 03 (точные даты). `paid` из ОСВ оставлен для сверки (DATA-8).
- **Сверка с исходными файлами (DATA-8):** `python -m tns.data.panel_check --month ГГГГ-ММ` → `panel_check.xlsx`. Сальдо, начисления, оплаты ОСВ и `dz` совпадают с файлом 02 во всех ячейках, `paid_payments` — с файлом 03. `paid` (ОСВ) и `paid_payments` (03) расходятся в ~0,3 % строк: перенос оплаты конца месяца на соседний месяц, оплаты декабря 2024 в январе, оплаты марта 2026, ещё не проведённые в ОСВ, и завышенное «Оплачено» ОСВ (в основном октябрь 2025), которое не подтверждается сальдо. Поэтому в расчётах `paid` из ОСВ не используется.
- Объём: ~150 тыс. ЛС × 15 мес. ≈ 2,3 млн строк.

## 3. `measure_events` — журнал мер

Источник — файлы 04–13. Меры вводятся **не чаще одного раза в месяц** по каждой мере. Несколько строк одного ЛС по одной мере в одном месяце сворачиваются в одну, исходное число строк сохраняется в `n_raw`, итог — в отчёт о качестве.

| Колонка | Тип | Смысл | Откуда / как считаем | known_at |
|---|---|---|---|---|
| `ls` | int64 | номер ЛС | 04–13 | — |
| `measure` | category | ключ меры | имя файла | — |
| `month` | datetime | месяц меры | `event_date` | — |
| `event_date` | datetime | первая дата меры в месяце | 04–13 | end (для M) |
| `date_precision` | category | `month` (autodial, email, sms, claim, visit — дата всегда 1-е) / `day` | справочник в коде | — |
| `n_raw` | int64 | сколько строк было в исходном файле за месяц | 04–13 | end |
| `dz_at_event` | float64 | `dz` на 01 месяца меры | panel | start |
| `window_end` | datetime | конец окна результата (P-04), включительно: по `result.window` — конец месяца меры (`month_end`, по умолчанию), конец следующего месяца (`next_month_end`) или N дней с начала окна (`days`, N = `result.days`) | расчёт | — |
| `paid_in_window` | float64 | оплаты с `event_date` по `window_end` (для точности `month` — с 1-го числа) | 03 | end |
| `result_30pct` | boolean | результат меры (P-03): `paid_in_window ≥ X × dz_at_event`, X = `result.share` (сейчас 0.30). `<NA>`, если долга нет или окно кончается позже последнего месяца данных | расчёт | end |

**Результат меры (P-03, P-04, DATA-6).** Параметры — раздел `result` в `configs/settings.yaml`: доля X (`share`), вид окна (`window`) и N дней (`days`). Окно открывается в день меры, для мер с точностью `month` — 1-го числа. Название колонки `result_30pct` историческое: при другом X в ней результат по новой доле.

Кто читает: стадии (переходы T-2→3, T-3→4, даты цикла), движок (EX-06, EX-08, R-VST-03, P-09), ML (признаки по прошлым мерам, только месяцы ≤ M−1).

**Повторные уведомления в истории.** 72 % ЛС с уведомлениями получали их больше одного раза, у 125 ЛС уведомление стоит каждый месяц. По регламенту уведомление в цикле одно. В журнале повторы остаются как есть (это факт истории). Машина стадий берёт **первое** уведомление цикла, а движок повторное уведомление в цикле не назначает (R-NTC-01).

## 4. `stages` — стадии

Стадия на **01.M**, до мер месяца M. Строит `tns/rules/stages.py` проходом по месяцам с 2025-01. Используются только данные до 01.M: меры месяца M−1 становятся известны на 01.M.

**Как считается (решения от 06.11.2026):**
1. **Стадия по фактам** (`stage_fact`) — самая тяжёлая мера текущего цикла: информирование → S1, уведомление → S2, ограничение → S3, заявление в суд → S4, приказ / ИЛ → S5 (`stages.measure_stage` в `configs/settings.yaml`).
2. **База** — бо́льшая из стадии по фактам и стадии прошлого месяца. **Откатов нет** (T-*→1 выключен, `stages.rollbacks: false`).
3. **Погашение** — если сработал переход в S0 (T-*→0, «dz < P-01»), ЛС уходит в S0, цикл закрывается, даты цикла сбрасываются (кроме `last_claim_date`).
4. Иначе **не больше одного шага вперёд**: первый сработавший переход с листа «Переходы» (T-0→1, T-1→2, T-2→3, T-3→4, …). Условия вычисляются прямо из таблицы правил (`tns/rules/conditions.py`).
5. **Исключения пока не учитываются** (`stages.exceptions: false`), стадии SX нет, `exception_codes` пустая.

**Цикл** — от выхода из S0 до погашения (возврат в S0). Меры прошлых циклов на стадию не влияют.

Как вычисляются поля условий: `result(info)` — `pay30_m` прошлого месяца; `result(notice)` — `result_30pct` первого уведомления цикла; `result(restriction)` — последнего ограничения цикла; `months_in_stage` в условиях — полные месяцы в стадии до M; `court_threshold_ok` — выполнены пороги хотя бы одного активного правила R-CRT-*; `contract_active` — `stages.field_defaults`.

Январь 2025 — «разогрев»: срок просрочки ещё не определён, все ЛС в S0 (`stage_source = start`).

| Колонка | Тип | Смысл | known_at |
|---|---|---|---|
| `ls` | int64 | номер ЛС | — |
| `month` | datetime | месяц | — |
| `stage` | category | итоговая стадия на месяц: `S0`–`S5` (`SX` зарезервирована). По ней движок выбирает меры | start |
| `stage_prev` | category | стадия на 01.(M−1); пусто в первом месяце данных | start |
| `stage_fact` | category | стадия только по мерам текущего цикла (до сброса при погашении) | start |
| `stage_source` | category | откуда стадия: `start` — первый месяц данных, `rule` — переход по правилу, `fact` — поднята по факту меры, `carry` — сохранена с прошлого месяца | start |
| `months_in_stage` | int64 | сколько месяцев подряд в `stage`, включая M | start |
| `transition` | string | код перехода T-… на 01.M, пусто — без перехода | start |
| `exception_codes` | string | сработавшие EX-… через `;` (пока всегда пусто) | start |
| `cycle_id` | int64 | номер цикла взыскания ЛС (0 — долга ещё не было); растёт при каждом выходе из S0 | start |

| `notice_date` | datetime | первое уведомление в текущем цикле | start |
| `restriction_date` | datetime | последнее ограничение в текущем цикле | start |
| `court_application_date` | datetime | последнее заявление в суд в текущем цикле | start |
| `court_result_date` | datetime | последний приказ / ИЛ в текущем цикле | start |
| `last_claim_date` | datetime | последняя претензия (для P-09); при погашении не сбрасывается | start |
| `reason` | string | объяснение стадии по-русски. Заполнено в строках `rule` и `fact` и во всех строках месяца плана | start |
| `rules_version` | string | версия таблицы правил: `v0.3 (sha256…)` | — |

Даты цикла — только события до 01.M. Нет события — `NaT`.

Шаг пайплайна возвращает строки за месяцы **до месяца плана включительно** (вся история нужна ML как признак). Движку нужна только `month == месяц плана`. Полная история хранится в кэше `output/cache/stages_history.parquet` и пересчитывается, только если изменились панель, журнал мер, таблица правил или раздел `stages` настроек. Для людей — `output/<ГГГГ-ММ>/stages.xlsx`: «Сводка», «Текущая стадия» (одна строка на ЛС), «Переходы» (все изменения стадии: по правилу и «по факту»).

## 5. `candidates` — кандидаты на меры

Только меры, которые **разрешены** правилами для ЛС в месяце M, и почему. Отказы (какие меры нельзя и почему) не пишем.

| Колонка | Тип | Смысл | Откуда |
|---|---|---|---|
| `ls` | int64 | номер ЛС | — |
| `month` | datetime | месяц плана | — |
| `measure` | category | ключ меры | лист «Правила» |
| `rule_codes` | string | сработавшие правила через `;` | лист «Правила» |
| `stage` | category | стадия на 01.M | stages |
| `dz` | float64 | долг на 01.M | panel |
| `overdue_m` | Int64 | срок просрочки | panel |
| `is_background` | boolean | фоновая мера | колонка «Фоновая?» |

| `rules_version` | string | версия таблицы правил | — |

Объяснение движка — только «почему мера разрешена» (сумма долга, срок, стадия, условие). Судьбу меры (назначена или снята по лимиту) дописывает аллокатор.

## 6. `score` — скор

Вероятность, что ЛС сам оплатит ≥ 30 % от `dz` до конца месяца M (= `pay30_m`). Скорятся **все ЛС с `dz ≥ P-01`** на месяц M, а не только кандидаты. Скор один на ЛС, без привязки к мере.

| Колонка | Тип | Смысл |
|---|---|---|
| `ls` | int64 | номер ЛС |
| `month` | datetime | месяц |
| `p_pay` | float64 | калиброванная вероятность, 0…1 |
| `top_factors_text` | string | три фразы через `;` с русскими названиями признаков |
| `top_factors_json` | string | `[{"feature", "name_ru", "value", "contribution"}]` |
| `model_version` | string | версия модели |
| `train_months` | string | месяцы обучения, например `2025-07..2025-10` |
| `scored_at` | datetime | когда посчитан скор |
| `y_true` | boolean | факт `pay30_m`, только в бэктесте; в рабочем запуске `<NA>` |

Приоритет в скоре не считается, это делает аллокатор.

## 7. `plan` — выход аллокатора (справочно)

Здесь фиксируется только то, что следует из решений выше. Детали — в SVC-1.

- Приоритет считает аллокатор: `priority = dz × (1 − p_pay)`. Формула и режим (`debt` — текущая практика по убыванию `dz`, `score` — по приоритету) задаются в `settings.yaml`.
- `plan.parquet` — все кандидаты с колонками `status` (`assigned` / `limit_cut`), `queue_rank`, `queue_size`, `priority`, `explanation` = `explanation_rules` + судьба меры, например «назначено, место 412 из 1 550» или «снято по лимиту, место 1 803 из 1 550».
- Реестры по мерам (Excel) содержат только `assigned`.
