# Объяснение проекта: ML-система рекомендаций мер взыскания долгов для ТНС Энерго

> **Кому это:** junior data scientist / product manager  
> **От кого:** senior ML engineer, разработавший систему с нуля  
> **Цель:** понять систему настолько, чтобы объяснить её директору и воспроизвести самостоятельно

---

## 1. Общая идея проекта (Big Picture)

### Какую проблему мы решаем

ТНС Энерго — энергетическая компания. У неё есть **тысячи должников** — абонентов, которые не платят за электричество. Для каждого должника можно применить разные меры взыскания: послать SMS, позвонить, ограничить подачу электроэнергии, подать в суд и т.д.

**Проблема старого подхода:** все эти меры применяются по очереди, вслепую — сначала SMS всем, потом звонок всем, потом визит всем. Это дорого, неэффективно и нарушает правила (например, нельзя идти в суд, если до этого не было предупреждения об ограничении).

**Наше решение:** вместо "всем одно и то же" — каждому абоненту **индивидуальная рекомендация** той меры, которая с максимальной вероятностью заставит именно его заплатить, с учётом его профиля, истории и бюджетных ограничений компании.

### Для кого это

- **Для бизнеса (ТНС Энерго):** максимизировать сбор долгов при ограниченном бюджете и мощностях (у колл-центра, у выездной бригады — ограниченное количество контактов в месяц)
- **Для операционной команды:** получить готовый список — кому что делать в этом месяце

### Ценность (Value Proposition)

> Система превращает хаотичный процесс взыскания в **управляемый ML-конвейер**, который говорит: "Этому абоненту — SMS и автодозвон, этому — визит, а этому уже пора в суд."

Ключевые выгоды:
- **Выше возврат долгов** — деньги тратятся на меры, которые реально работают для конкретного человека
- **Дешевле операционно** — дорогие меры (визит, суд) идут только тем, кому они нужны
- **Соответствие закону** — правила применения мер жёстко зашиты в систему, нарушения исключены автоматически

### Шаг 1: Построение признаков (`build_kprototypes_features.py`)

**Что происходит:**  
Из сырых Excel-файлов создаётся единая таблица — "портрет" каждого абонента. Одна строка = один лицевой счёт (ЛС). Признаков около 80+.

**Зачем это нужно:**  
Без этого у нас просто разрозненные данные: "абонент Иванов" — в одном файле, его долг — в другом, история платежей — в третьем. Мы собираем это всё в одно место.

**Что входит в "портрет":**

| Источник данных | Что мы узнаём |
|-----------------|----------------|
| Файл 01 (общая инфо) | Есть ли телефон, email, льготы, тип жилья, город/деревня |
| Файл 02 (ОСВ — обороты по счёту) | Текущий долг, средние начисления за 12/6/3 мес., тренд долга, сколько месяцев подряд не платит |
| Файл 03 (платежи) | Дата последнего платежа, регулярность, способ оплаты, сумма |
| Файлы 04–13 (меры) | Какие меры уже применялись, на каком этапе взыскания находится |

**Почему именно такой набор признаков:**  
- `overdue_months` (сколько месяцев подряд задолжал) — главный предиктор риска  
- `avg_accrual_12m` (среднее начисление) — нужно для расчёта денежного эффекта мер  
- `has_phone`, `has_email` — некоторые меры физически невозможны без контакта  
- История мер — закон запрещает суд без предшествующих уведомлений

**Инструменты:** `pandas`, `openpyxl` для чтения Excel  
**Почему не SQL:** данные приходят как Excel — именно так их передаёт бизнес

### Шаг 2: Кластеризация (`run_kprototypes_segmentation.py`)

**Что происходит:**  
Все абоненты разбиваются на **6 кластеров (сегментов)** по схожести профиля.

**Зачем это нужно:**  
Представь, что у тебя 150 000 должников. Работать с каждым индивидуально — слишком сложно. Зато если разбить их на типы, ты понимаешь: "Сегмент 0 — это молодые городские жители с небольшим долгом, они хорошо реагируют на SMS. Сегмент 4 — злостные многолетние должники в деревне, у которых нет email и которые реагируют только на визит."

**Какой алгоритм используется: K-Prototypes**  
Это гибрид двух алгоритмов: K-Means (для числовых данных) + K-Modes (для категориальных).

**Почему не обычный K-Means:**  
K-Means работает только с числами. У нас есть категориальные признаки: тип жилья (`квартира`/`дом`), способ оплаты (`карта`/`наличные`/`банк`), город/деревня. K-Means их не умеет обрабатывать нормально — пришлось бы делать `OneHotEncoding`, который ломает расстояние между кластерами.

**Почему K=6:**  
Подбирался экспериментально. 6 кластеров — это компромисс между: "мало = все смешаны, нет инсайтов" и "много = сложно интерпретировать, нестабильно".

**Инструменты:** библиотека `kmodes` (специально для смешанных данных)

**Что получаем на выходе:**
- `kprototypes_labels.csv`: `ЛС → сегмент (0..5)`  
- `kprototypes_segment_profile.csv`: усреднённый профиль каждого сегмента  

**"Горячие" сегменты:**  
По умолчанию сегменты 0 и 1 — "горячие". Это значит, что при распределении ограниченных мер они получают приоритет. Логика: именно у этих абонентов максимальный суммарный долг или наибольшая вероятность погашения при правильном воздействии.

### Шаг 3: Uplift-модели (`build_response_models.py`)

**Это самый важный и нетривиальный шаг — остановимся подробно.**

#### Что такое uplift и зачем он нужен

Обычная ML-модель отвечает на вопрос: "Заплатит ли этот человек?"  
Наша модель отвечает на другой вопрос: **"На сколько БОЛЬШЕ вероятность, что он заплатит, ЕСЛИ мы применим эту меру?"**

Это называется **uplift** (инкрементальный эффект). Разница важна:

> Абонент Петров платит сам по себе в 80% случаев. Если мы пошлём ему SMS, он заплатит в 82% случаев. Uplift = +2%. Незачем тратить на него ресурсы.  
>
> Абонент Сидоров платит сам по себе в 10% случаев. После SMS — 40%. Uplift = +30%. Вот кому нужно отправить SMS.

#### Как строится модель: T-Learner

Для каждой из 9 мер (SMS, email, автодозвон, звонок оператора, уведомление об ограничении, ограничение, визит, требование, судебный приказ) строятся **три модели LightGBM:**

```
mu1(X) = P(заплатит в течение 30 дней | мера ПРИМЕНЕНА, признаки X)
mu0(X) = P(заплатит в течение 30 дней | мера НЕ применялась, признаки X)

uplift(X) = mu1(X) - mu0(X)
```

**Как строится обучающий датасет:**
- **Обработанные (treated):** абоненты, которым реально применили меру в историческом периоде
- **Контрольная группа (control):** абоненты, которым эту меру **не** применяли. Им присваиваются случайные "фиктивные" даты события из распределения дат treated — чтобы временной контекст был одинаковым
- **Целевая переменная:** заплатил ли абонент в течение **30 дней** после (реальной или фиктивной) даты события

**Почему LightGBM, а не, например, логистическая регрессия:**
- Обрабатывает нелинейные зависимости (например, "средняя сумма долга × количество детей → вероятность оплаты")
- Быстро обучается на больших данных
- Хорошо работает без сложной нормализации числовых признаков
- Встроенное обнаружение важности признаков

**Почему T-Learner, а не X-Learner или DR-Learner:**  
T-Learner проще, прозрачнее, и при достаточном размере данных даёт результаты, сравнимые с более сложными методами. X-Learner лучше работает при сильном дисбалансе treated/control — пока данных достаточно, T-Learner достаточен.

#### Ожидаемый денежный эффект (ERG — Expected Recovery Gain)

После расчёта uplift мы переводим его в рубли:

```
ERG = uplift × avg_accrual_12m
```

Логика: если uplift для SMS у данного абонента = 0.15 (на 15% больше вероятность оплаты), а его среднее начисление за месяц = 5000 руб., то ожидаемый прирост сбора = **750 рублей**.

Это позволяет сравнивать меры между собой в деньгах. Лучше выбрать SMS с ERG = 700 руб., чем визит с ERG = 300 руб. (а визит ещё и дороже).

**Дополнительная модель: propensity**  
Третья LightGBM-модель оценивает `P(мера применялась | X)` — вероятность того, что абонент "отобрался" для этой меры. Это нужно для документирования **selection bias**: если у treated и control принципиально разные профили, uplift-оценка ненадёжна. Очень высокий propensity AUC (например, 0.9+) — красный флаг.

**Что получаем на выходе:**
- `utility_matrix.csv`: для каждого абонента и каждой меры — `uplift_мера`, `expected_recovery_gain_мера`, `cost_tier_мера`
- 27 файлов `.joblib`: сохранённые модели (mu0, mu1, propensity для 9 мер)

### Шаг 4: Рекомендации (`build_recommendations.py`)

**Что происходит:**  
Из всего вычисленного выше формируется итоговый список: "кому — что делать в этом месяце".

**Алгоритм состоит из 5 блоков:**

#### Блок 1: Определение стадии (state machine)

Для каждого абонента определяется, на какой стадии взыскания он находится:
- `informing` — ещё только уведомляем (email, SMS, автодозвон)
- `restriction_notice` — уже предупредили об ограничении
- `restriction_or_impossible` — ограничение применено или невозможно (льготники, газ)
- Это важно, потому что закон требует последовательности: нельзя сразу идти в суд, минуя предупреждение

#### Блок 2: Проверка допустимости (eligibility)

Для каждой меры для каждого абонента проверяется список правил из `rules.yaml`:

```yaml
# Пример правила для визита:
visit:
  min_overdue_months: 2        # минимум 2 месяца просрочки
  min_dz: 1000                 # долг >= 1000 руб.
  requires_phone: false         # не требует телефона
  requires_prev_stage: informing  # должен быть на стадии уведомления
```

Если хоть одно правило нарушено — мера не рекомендуется этому абоненту.

#### Блок 3: Формирование пакета мер (action set)

Для каждого допустимого абонента составляется **пакет**:
- **Фоновые меры** (email + автодозвон) — всегда, если технически возможны, потому что они дёшевы и ненавязчивы
- **Ведущая мера** — одна, с максимальным ERG среди допустимых, при условии что `ERG > 0`

Пример:
> Абоненту Иванову допустимы: SMS (ERG=400 руб.), визит (ERG=800 руб.), требование (ERG=200 руб.)  
> Пакет: email + автодозвон + **визит** (как ведущая мера с максимальным ERG)

#### Блок 4: Жадное распределение (greedy allocator)

У компании есть лимиты — сколько раз в месяц можно применить каждую меру (`limits.yaml`):

```yaml
limits:
  autodial: 8000
  sms: 2150
  visit: 500
  restriction: 200
  email: null   # без ограничений
```

Алгоритм жадного распределения:
1. Сначала обрабатываются "горячие" сегменты (0, 1)
2. Внутри сегмента — сортировка по ERG (убыванию)
3. Берём следующего абонента, если для его ведущей меры ещё есть квота — назначаем
4. Если квоты нет — оставляем только фоновые меры

**Почему жадный, а не оптимальный (LP/ILP):**  
Жадный алгоритм работает за секунды, детерминирован и понятен. Оптимизация через линейное программирование дала бы теоретически лучший результат, но: дольше, сложнее объяснить бизнесу, и разница на практике небольшая.

#### Блок 5: Объяснения

Каждая рекомендация сопровождается текстом на русском языке:
> "Рекомендуется визит. Ожидаемый прирост сбора: 750 руб. Причина: высокий uplift для данного сегмента, 4 месяца просрочки, нет контактных данных для дистанционных мер."

## 3. Данные

### Откуда берутся данные

Все данные — из Excel/CSV файлов, предоставленных ТНС Энерго:

| Файл | Содержание |
|------|------------|
| 01 | Общая информация о лицевых счётах |
| 02 | ОСВ (обороты по счёту) — начисления и оплаты по месяцам |
| 03 | Детализация платежей |
| 04–13 | История применения каждой меры взыскания |

### Как обрабатываются данные

1. **Чтение:** `pandas.read_excel` / `read_csv`
2. **Объединение:** по ключу `LS` (лицевой счёт) через `merge`/`join`
3. **Расчёт фичей:** rolling windows (12/6/3 месяца) для трендов
4. **Импутация пропусков:** для кластеризации — медианы для числовых, `"Unknown"` для категориальных (K-Prototypes не умеет работать с NaN)

### Проблемы в данных

| Проблема | Как решаем |
|----------|------------|
| Пропущенные значения (нет телефона, нет email) | Флаги `has_phone`, `has_email` + imputation |
| Дубликаты ЛС в разных источниках | `groupby` + агрегация |
| Разные форматы дат в Excel | `pd.to_datetime` с `dayfirst=True` |
| "Мёртвые" ЛС без активности | Опциональный фильтр `--delinquent-only` |
| Selection bias в контрольной группе | Контролируется через propensity AUC |

## 4. Модели / алгоритмы

### Полный список

| Модель | Где | Зачем |
|--------|-----|-------|
| K-Prototypes | Шаг 2 | Кластеризация должников |
| LightGBM (mu1) | Шаг 3 | P(оплата | мера применена, X) |
| LightGBM (mu0) | Шаг 3 | P(оплата | мера НЕ применена, X) |
| LightGBM (propensity) | Шаг 3 | P(мера применена | X) — диагностика |
| Правила из YAML | Шаг 4 | Бизнес/правовые ограничения |
| Жадный алгоритм | Шаг 4 | Распределение в рамках лимитов |

### Обучение uplift-моделей

```
Для каждой из 9 мер:
  1. Взять историю за последние N месяцев (TREATMENT_WINDOW_START..END)
  2. Разметить treated (мера была) и control (мера не была, случайная дата)
  3. Проставить целевую переменную: оплата в течение 30 дней
  4. 5-кратная кросс-валидация → оценка качества
  5. Обучить финальную модель на всех данных
  6. Сохранить .joblib
```

### Метрики и почему именно они

| Метрика | Для чего | Почему |
|---------|----------|--------|
| AUC ROC (mu1/mu0) | Качество uplift-модели | Стандарт для бинарной классификации; не зависит от порога |
| Propensity AUC | Диагностика | Высокий AUC = большой selection bias = осторожно с uplift |
| Naive lift | Быстрая проверка | Платят ли treated лучше control в среднем — без ML |
| ERG в рублях | Бизнес-метрика | Единственное, что важно для бизнеса |

**Как понять, что модель "хорошая":**
- AUC mu1 и mu0 > 0.6 — модель лучше случайного
- Propensity AUC не слишком высокий (< 0.85) — control группа похожа на treated
- Naive lift > 0 — treated действительно платят лучше control
- ERG > 0 хотя бы у 30–50% абонентов — мера вообще работает

## 5. Инференс и продакшн-логика

### Как работает prediction

Модели уже обучены и сохранены в `models/`. При запуске `build_recommendations.py`:

```python
# Загрузка
model = joblib.load("models/mu1_sms.joblib")

# Prediction на всех ЛС
features = feature_table[FEATURE_COLS]
prob_treated = model.predict(features)   # mu1(X)
```

То же для mu0. Uplift = mu1 - mu0 для каждого абонента.

### Как обрабатываются edge cases

| Ситуация | Обработка |
|----------|-----------|
| Абонент не попадает ни под одну допустимую меру | Получает только фоновые (email/autodial) или пустую рекомендацию |
| ERG ≤ 0 для всех мер | Ведущая мера не назначается, только фоновые |
| Лимит по мере исчерпан | Переходит к следующей мере по ERG |
| Отсутствует лицевой счёт в utility_matrix | Пропускается с предупреждением |
| Нет истории сегментации | Все считаются "холодными" |

### GUI-интерфейс (`interface.py`)

Для операционной команды, которая не хочет запускать консоль, есть графический интерфейс на PySide6. Кнопки:
- "Запустить всё" — запускает все 4 шага последовательно
- "Шаг 1 — признаки" — только feature engineering
- Просмотр логов в реальном времени
- Открыть папку с результатами

Под капотом GUI просто запускает те же Python-скрипты через `subprocess`.

## 6. Сильные стороны проекта

### С точки зрения продукта

**1. Из "кому что" в "кому что и почему выгодно"**  
Система не просто рекомендует меру — она говорит, сколько рублей ожидается. Бизнес может принимать решение о ROI: "700 рублей ожидаемого сбора при стоимости визита 500 рублей — стоит ли?"

**2. Операционные ограничения зашиты внутрь**  
Нельзя рекомендовать больше 500 визитов в месяц — потому что выездных сотрудников ровно столько. Система знает это и не перегружает команду.

**3. Закон соблюдается автоматически**  
Нет человека, который должен помнить "нельзя идти в суд без уведомления". Правила прошиты в YAML и применяются к каждой рекомендации.

**4. Интерпретируемые сегменты**  
6 сегментов с понятными профилями помогают маркетингу и аналитикам понять "кто наши должники" вне зависимости от ML.

**5. Масштабируемость**  
Система обрабатывает 150 000+ лицевых счётов. Добавить новую меру — нужно добавить файл истории, строку в YAML и запись в `MEASURE_META`.

### В каких сценариях система особенно эффективна

- **При ограниченных ресурсах:** 500 визитов на 50 000 должников — система выбирает именно тех 500, от которых ожидается максимальный эффект
- **При неоднородных должниках:** система находит, что одним помогает SMS, другим — только личный контакт
- **При юридической сложности:** автоматическая проверка правил взыскания снижает риск штрафов

## 7. Ограничения и риски

### Где система может давать сбои

**1. Selection bias (главный риск)**  
Контрольная группа строится не из рандомизированного эксперимента, а из "кому не применяли меру". Проблема: возможно, им не применяли именно потому, что они уже сами платили. Это занижает uplift.  
*Индикатор:* propensity AUC > 0.85 для какой-то меры → её uplift-оценкам доверять меньше.

**2. Один срез данных**  
Модели обучены на исторических данных. Если поведение должников изменилось (например, экономический кризис), модели устаревают.  
*Решение:* переобучать модели при каждом новом запуске (данные за новый период).

**3. Холодный старт для новых мер**  
Если компания хочет добавить новую меру (например, мессенджер-уведомления), у неё нет исторических данных — uplift не рассчитать.  
*Решение:* A/B тест на небольшой группе → накопить данные → обучить модель.

**4. Сегменты нестабильны при малых данных**  
Если в следующем месяце существенно изменился состав должников, кластеры могут "перемешаться". Переобучение K-Prototypes — дорогая операция.

**5. ERG ≠ реальная выручка**  
`uplift × avg_accrual_12m` — это оценка, не гарантия. Абонент может заплатить частично или не заплатить вовсе.

### Что можно улучшить

| Улучшение | Эффект | Сложность |
|-----------|--------|-----------|
| Перейти на DR-Learner или X-Learner | Меньше bias при дисбалансе данных | Средняя |
| Добавить стоимость мер в целевую функцию | ROI-оптимизация вместо ERG | Средняя |
| Использовать Linear Programming для allocator | Оптимальное распределение | Высокая |
| Онлайн-обновление моделей | Более свежие оценки | Высокая |
| Добавить LTV в ERG | Учёт долгосрочной ценности клиента | Средняя |

## 8. Как объяснить это продукт менеджеру

### Аналогия: магазин с ограниченными промоакциями

Представь, что ты управляешь магазином, в котором есть должники — люди, которые взяли товар в кредит и не платят. У тебя есть несколько инструментов воздействия:

- **Письмо на email** — дёшево, почти бесплатно
- **Звонок робота** — дёшево, но люди устают
- **Звонок живого менеджера** — дороже
- **Визит домой** — дорого, мало сотрудников
- **Суд** — очень дорого, долго

Раньше: всем сначала письмо, потом звонок робота, потом звонок человека и т.д. по очереди.

**Наша система:** смотрит на каждого должника и говорит — "Этот человек скорее всего сам заплатит, достаточно письма. А вот этому нужно позвонить живому — он реагирует только так. А третий уже 8 месяцев не платит и не реагирует ни на что — пора в суд."

И всё это — с учётом того, что звонить живому человеку можно только 1000 раз в месяц. Система сама решает, кому из всех достанется этот звонок.

### Ключевые цифры для презентации

- **150 000+** лицевых счётов обрабатываются за один запуск
- **9 видов мер** оцениваются для каждого абонента
- **ERG в рублях** — понятная для бизнеса метрика результата
- **4 шага пайплайна**, полностью автоматизированные
- **6 типов должников** — понятные сегменты для операционной команды

### Что говорить стейкхолдерам

> "Мы перестали стрелять из пушки по воробьям. Теперь для каждого должника система выбирает ту меру, которая с наибольшей вероятностью принесёт деньги — и делает это в рамках бюджета и закона."
